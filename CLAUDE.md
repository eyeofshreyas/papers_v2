# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build System

Papers uses **Meson** as its build system with Rust components managed through the workspace. The build directory is `build/` (already configured).

```bash
# Configure (first time or after meson.build changes)
meson setup build -Dprofile=devel

# Build
meson compile -C build

# Run tests
meson test -C build

# Run a single C test
meson test -C build pps-jobs-test

# Install (for system-wide)
meson install -C build
```

For rust-analyzer IDE support, use `meson devenv`:
```bash
meson devenv -C build
code ..
```

## Code Formatting

- **C**: `clang-format` (run before committing)
- **Rust**: `rustfmt` (run before committing)

## Architecture

The project has two C libraries and a Rust application shell layered on top:

```
libdocument/          C library — document format abstraction layer (PpsDocument GObject,
                      interfaces: DocumentFind, DocumentAnnotations, etc.)
libdocument/backend/  Pluggable format backends (PDF via poppler, DjVu, TIFF, comics)

libview/              C library — rendering widgets (PpsView, PpsJob scheduler,
                      page/pixbuf caching, annotation overlays, print operations)

rust/papers-document/ GObject-Introspection Rust bindings for libdocument (generated by gir)
rust/papers-view/     GObject-Introspection Rust bindings for libview (generated by gir)

shell/                Rust GTK4/libadwaita application (the Papers binary)
thumbnailer/          Rust thumbnail generator for file managers
previewer/            C print previewer
nautilus/             Nautilus extension for document property pages
```

### Shell module map (`shell/src/`)

The shell is a standard GNOME app pattern. Key modules:
- `application.rs` — `PpsApplication`, app lifecycle
- `window.rs` — `PpsWindow`, top-level window
- `document_view.rs` — `PpsDocumentView`, central widget combining the view, sidebar, toolbar; owns the `DocumentModel`
- `sidebar*.rs` — individual sidebar panels (links, thumbnails, annotations, layers, attachments, chat)
- `sidebar_chat.rs` — AI chat panel using Ollama for local LLM inference against document text

### UI files

UI is defined in Blueprint (`.blp`) files under `shell/resources/` and `libview/`. These are compiled to `.ui` XML at build time by `blueprint-compiler`. Always edit `.blp` files, not the generated `.ui` files.

## Rust Bindings

Bindings in `rust/papers-document/` and `rust/papers-view/` are **generated by gir** — do not hand-edit files in their `src/auto/` directories. Edit `Gir.toml` to control generation, then regenerate:

```bash
meson compile -C build update-rust-bindings
```

When resolving binding conflicts in rebases: fix only `Gir.toml`, then regenerate rather than manually resolving auto-generated files.

## Debugging

```bash
# Enable all debug messages
PPS_DEBUG=1 papers document.pdf

# Debug job scheduling
PPS_DEBUG_JOBS=1 papers document.pdf

# Show element borders (useful for rendering issues)
# Values: chars links forms annots images media selections
PPS_DEBUG=borders PPS_DEBUG_SHOW_BORDERS=annots papers

# Debug Poppler rendering
G_MESSAGES_DEBUG=Poppler papers document.pdf
```

## Commit Message Format

```
subsystem: brief description (≤72 chars, no trailing period)

Body explaining the why. Wrap at 80 columns.

Closes #1234
```

Subsystem prefixes: `shell`, `libdocument`, `libview`, `libmisc`, `backends`, `build`, `doc`, `flatpak`.

## Meson Options

Notable options when configuring:
- `-Dprofile=devel` — enables development app ID (`org.gnome.Papers.Devel`)
- `-Dintrospection=enabled` — required for updating Rust bindings
- `-Dpdf=enabled/disabled` — PDF backend (via poppler ≥ 25.07.0)
- `-Dfile_tests=true` — enables libview C tests
- `-Dkeyring=enabled/disabled` — GNOME Keyring/oo7 integration

## AI Chat Feature (active development)

`shell/src/sidebar_chat.rs` and `shell/resources/pps-sidebar-chat.blp` implement an Ollama-based AI chat sidebar. It connects to `http://localhost:11434`, auto-starts the `ollama serve` process if needed, and uses the `gemma4` model. Document text context (up to 16 000 chars) is injected into the system prompt.
